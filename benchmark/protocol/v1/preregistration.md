# Benchmark V1 Preregistration

Status: **draft, pending freeze**. No model run or jury result exists.

## Research Question

Under an identical model snapshot, executable starter, fact packet, original
asset packet, tool surface, and budget, does Frontend Design Ultra improve blind
human preference without reducing shipping quality?

## Dataset Plan

The scored V1 target is 30 briefs: 20 public and 10 sealed holdout. The intended
industries are hospitality, legal, finance, healthcare, SaaS, e-commerce,
culture/editorial, local services, B2B/industrial, and creative/portfolio. Each
industry should cover greenfield, constrained-brand, and redesign work.

This MVP contains six public calibration briefs only. They exercise the
validated protocol, anonymization, commitment, and result-manifest contracts.
Runner and capture execution remain pending and the fixtures are excluded from
leadership claims. Deterministic scoring and fail-closed publication contracts
are implemented but contain no result data.

## Conditions

Four conditions are declared. Exact external competitors, commits, licenses,
installation methods, and effective-context hashes must be frozen before the
matrix is locked. A condition receives its documented native capabilities when
those capabilities can operate inside the common tool and budget contract.

## Common Inputs

- one frozen model snapshot and sampling configuration;
- one starter commit and lockfile;
- identical facts and required content;
- identical original, licensed, or otherwise permitted assets with documented
  benchmark-use and publication rights;
- identical browser/tool permissions;
- identical token, tool-call, wall-clock, and repair-loop budgets;
- no human code edits;
- no live research or image generation in the primary track.

## Run Sequence

Each declared run slot is generated before execution. A run records the initial
build and every allowed repair checkpoint. The final checkpoint is the primary
creative endpoint; first-pass quality and repair cost are secondary measures.

Build, agent, or condition failures count as failures. Only a documented
provider or capture-infrastructure failure may be retried. The original failed
attempt is retained. A capture-only failure may recapture the exact build but
must not regenerate it.

## Blindness

The holdout prevents benchmark authors from tuning the skill to all scored
briefs before execution. The jury is separately blinded to condition identity.
The builder necessarily sees its assigned brief while producing the site.

Jury artifacts use keyed opaque IDs and keyed blind digests. Condition-named run
manifests and source content hashes remain embargoed until vote freeze. Page
content may not mention a skill, model, or condition. A visible condition leak
is recorded as a run defect; it is not manually painted out after capture.

## Outcomes

Primary outcome: Frontend Design Ultra versus baseline pairwise preference
share, ties counted as 0.5, with a 95% confidence interval clustered by brief.

Secondary outcomes include all-condition pairwise estimates, four creative
dimensions, shipping pass rate, completion rate, fabrication rate, build
failure, runtime defects, token usage, elapsed time, and repair loops.

Creative and shipping outcomes remain separate. A failed shipping gate is never
averaged into an attractive visual score.

## Freeze And Reveal

Before execution, publish a protocol tag and a salted commitment for the
canonical holdout bundle. Before unblinding, freeze the exact pseudonymous vote
files, blind packet, and delivered jury-evidence bytes in `vote-freeze.json`.
Then publish the mapping key and holdout salt through separate reveal artifacts.
The validator regenerates the blind mapping, verifies the original holdout
commitment, and recomputes the scorecard. Any substantive protocol or scoring
change creates a new benchmark version.

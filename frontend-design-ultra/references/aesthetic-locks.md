# Aesthetic Locks

Use when the work risks generic output, mixed visual doctrines, redesign drift, or implementation from vague taste.

## Taste Profile Object

Before substantial visual decisions, create this internal object:

```yaml
taste_profile:
  mode:
  domain:
  primary_lane:
  style_preset:
  support_archetype:
  variance: low | mid | high
  motion: low | mid | high
  density: low | mid | high
  evidence_depth: quick | standard | deep | brutal
  asset_mode: existing | generated | typography-led | proof-led
  hard_constraints:
```

If parameters conflict, resolve in this order: hard gates, explicit user goal, mode precedence, route job, asset reality, style preset, taste dials.

## Design-Plan Synthesis

For `/designplan`, `/implement` after design, `/image-to-code`, `/imagegen`, `/redesign`, or high-stakes visual work, produce a pre-build plan before code:

1. Page job and first-viewport promise.
2. Audience intent and conversion/trust spine.
3. Primary archetype and excluded archetypes.
4. Design system tokens and component primitives.
5. Section grammar and visual rhythm.
6. Motion scale and reduced-motion final state.
7. Evidence and acceptance checks.

Do not begin implementation if the plan lacks a lane, token contract, mobile composition, state coverage, or acceptance checks.

## Archetype Lock

Pick one primary archetype. Add only one support archetype when it solves a specific job.

- Minimal editorial: precision, negative space, restrained interaction.
- Industrial/brutalist: grid pressure, hard contrast, tactical rhythm.
- Soft premium: warm depth, refined surfaces, human polish.
- Product proof: visible product or workflow state before decoration.
- Editorial motion: kinetic hierarchy, one signature movement, strict fallback.
- Brandboard: identity proof, construction logic, system application.

Reject designs that mix multiple archetypes without clear hierarchy. Mixed style is allowed only when the user asks for contrast and each section has a defined role.

## Drift Detector

Before final output, compare the result against the taste profile:

- Palette: one dominant color world and one accent logic.
- Type: clear display/body/numeric roles, no accidental default stack.
- Shape: radius, stroke, shadow, and icon logic are consistent.
- Layout: each section has a job and avoids repeating the same default grid.
- Motion: one motion vocabulary, no effect bouquet.
- Proof: claims are backed by real assets, user-provided content, or marked assumptions.

If drift appears, either remove the drift or explain it as an intentional exception.

## Redesign Mutation Locks

Redesign must preserve working strengths before replacing weak systems:

- Preserve: functional flows, useful information architecture, recognized brand signals, real proof, working accessibility, performant interactions.
- Replace: generic hero, weak hierarchy, token drift, fake proof, repeated card grids, missing states, mobile squeeze, motion debt.
- Do not migrate stack or rebuild unrelated systems unless the user asks.
- Change the smallest surface set that fixes the root cause.
- Verify the new system against the original task, not against novelty.

## Anti-Default Locks

Block these unless intentionally justified:

- centered hero plus generic cards as the default solution
- default blue/purple glow gradients
- generic glass cards, blobs, fake badges, decorative dashboards
- Inter/Roboto/Arial/system UI as premium identity default
- placeholder logos, fake awards, fake customer numbers, fake screenshots
- repeated left-copy/right-image sections
- heavy scroll/3D effects without fallback and performance budget
- unreadable section images or collages used as implementation reference
